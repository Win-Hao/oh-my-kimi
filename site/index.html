GitHub 上叫 oh-my-kimi 的项目有 15 个。14 个是插件层，1 个是真 fork， 绝大多数已经停更。这个项目要占的是剩下那个空位。

调研

结论不是「这些人不行」，而是插件层有天花板。把 skill、hook、MCP server 配完，能做的事就到头了，项目自然停在那儿。

真 fork 没人做，原因也很实在：上游 kimi-code 近 30 天有 281 个提交，18 天发了 10 个版本。跟得住是件苦差事。

可行性

上游快，不等于跟不住

参照组是 oh-my-pi——它 fork 的上游 pi 近 7 天有 86 个提交， 比 kimi-code 的 73 还快。omp 在上面跑了 8 个月、653 个版本。

它的关键做法是把冲突面积锁死在包这一级：

omp 的 17 个包与上游的关系
agent · ai · coding-agent · tui继承自上游，冲突只发生在这 4 个
hashline · swarm · snapcompact · mnemopi · natives …全部是自己新开的包，永不冲突

它的招牌功能一个都没塞进上游的包里。

但也要看清终局。omp 的 porting-from-pi-mono.md 里， Last Sync Point 钉在 2026-03-22——五个月没同步了。 深度二开的尽头大概率是硬 fork。这个项目对此没有幻想，只是想把那一天推得尽量远。

做法

对上游的全部侵入：2 个文件，4 行

packages/omk/                 ← 我写的所有东西都在这，新文件永远不冲突
apps/kimi-code/src/main.ts    ← 顶部一行 import '@omk/core'    ┐ 全部
apps/kimi-code/package.json   ← devDeps 一行 @omk/core          ┘ 侵入

CI 里有一条检查专门守着这个约束：任何超出白名单的上游文件改动都会让构建失败， 强迫我先回答「能不能改成在 omk 里加个新东西」。

接缝是按 churn 数据选的，不是按顺手

下面是上游近 60 天的改动次数。挂载点选在冷的地方，功能写在冷的地方：

src/agent1971
src/app1370
src/session678
src/tui551
src/_base262
src/features235

单个文件更能说明问题：

agent-core-v2/src/index.ts69
kimi-code/src/main.ts6

index.ts 是 kimi 那套 import = register 架构的枢纽， 文件头自己写着「importing the package loads all scoped-registry registrations」—— 看起来正是该注册的地方，实际是全仓第一热点文件。挂在那上面等于天天解冲突。 main.ts 60 天只动了 6 次。

同步：merge，不是 rebase

./scripts/omk-sync.sh --dry   # 预览：多少新提交、哪些文件可能冲突
./scripts/omk-sync.sh         # 执行

这个 fork 不往上游提 PR，不需要干净的历史；而 merge 每次只处理增量， rebase 每次都要把全部改动重放一遍。脚本会先算出 我改过的文件 ∩ 上游这次改过的文件，冲突之前就告诉我。

每天或每两天跑一次。攒一周是 70 个提交，攒一个月是 280 个—— 冲突难度对间隔是超线性的。

DIVERGENCES.md

每次决定「这里要跟上游不一样」，立刻记一条 + 写清楚为什么。这张表是 fork 最重要的资产： 没有它，下次同步就会有人（包括三个月后的自己）把上游的写法又搬回来，然后疑惑为什么坏了。 这一招是从 omp 的移植指南第 15 节「Intentional Divergences」学来的。

现状

骨架已就位：独立包、接缝、同步脚本、分歧记录、CI 侵入面检查。第一个功能还没落地。

这个项目是一边加功能一边把 harness 内部拆开看懂，所以路线会跟着理解走， 不预先画一张假的 roadmap。进展看 提交历史。
